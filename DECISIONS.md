# Decisions

Judgment calls not specified in SPEC.md or the build instructions. One line of rationale each.

| # | Step | Decision | Rationale |
|---|---|---|---|
| 1 | 1 | Package named `value_sort`, built with hatchling. | Matches the product name in SPEC.md; hatchling is uv's default backend. |
| 2 | 1 | Only `pytest` declared; no runtime deps yet. | Working agreement: every new dependency is approved before it is added. |
| 3 | 1 | Unimplemented `make` targets exit 1 instead of no-op. | A target that silently succeeds could be mistaken for one that produced output. |
| 4 | 1 | Python pinned to 3.11 via uv-managed interpreter (`.python-version`). | System Python is 3.9; the spec calls for 3.11. |
| 5 | 2 | Metadata is streamed and only the six contract fields are written to `data/raw/meta_<Category>.slim.parquet`; the 2.47 GB JSONL is never stored. | User choice: disk footprint. The stream is sha256-verified against the published hash, so the slim file is provably from the source. |
| 6 | 2 | `categories` is not kept in the slim file. | User instruction: contract fields only. Anything needing it later (e.g. leaf-category candidate sets) requires a re-stream and a contract change. |
| 7 | 2 | `price`, `average_rating`, `rating_number`, `details` are stored as raw JSON text, not typed. | No silent coercion before Step 3; the loader owns typing and fails loudly. |
| 8 | 2 | C = unweighted mean of `average_rating`; m = median `rating_number`; both over items with rating_number >= 1. | Standard Bayesian-average prior; zero-rating items have no rating to average. Count-weighted C is reported for reference only. |
| 9 | 2 | Profile written to `reports/profile_<Category>.json` (committed). | Step 4 must read m and C from a versioned artifact, not a hardcoded value. |
| 10 | 6 | If Step 6 is reached, reviews are sampled by streaming the review JSONL and keeping only the top-N items' reviews; never downloaded in full. | User decision: the 11.4 GB review file is out of scope for this machine. |
| 11 | 2 | `PYTHONPATH=src` exported in the Makefile and `pythonpath = ["src"]` set for pytest. | uv flags the editable-install `.pth` as hidden on macOS and Python 3.11.16 ignores hidden `.pth` files; re-applied on every `uv run`, so it must be fixed in project config. |
| 12 | 4 | **SPEC amendment.** C and m are computed over the candidate set at rank time, not over the whole category. If a candidate set has < 30 items, fall back to global values and flag the result. | User decision: a protein powder should shrink toward comparable products, not the department average. Supersedes SPEC §3 "C = category mean rating" and Step 4's "m and C come from the Step 2 profile". |
| 13 | 7 | Candidate sets are built by title keyword match. No leaf categories, no re-stream. | User decision: with C/m per candidate set (#12), leaf categories aren't needed as a reference class. |
| 14 | 3 | Only items with a valid price > 0 enter ranking (`loader.priced`). | User decision: unpriced items don't appear in real results, and mixing them in makes z-scores inconsistent across rows. |
| 15 | 4 | The Step 4 sensitivity check varies C (simple mean, count-weighted mean, candidate-set mean) as well as m (25, 120, 500). | User decision. |
| 16 | 3 | Price rules: `—`, `from $X`, and ≤ 0 become null with a counted reason; outliers are kept unclipped; bad JSON or missing fields fail loudly. | User decision. Clipping would be a silent data edit; the log transform handles outliers. |
| 17 | 3 | Price strings that match none of the known patterns fail loudly; they are not nulled. | My call: an unforeseen format is exactly what should be surfaced, not quietly absorbed. None occur in this data. |
| 18 | 3 | Rows with empty or whitespace-only titles are dropped at load and counted (40 here). They aren't malformed and don't raise. | User decision: no title means the item can't be candidate-matched or pack-size parsed, so it can't take part in ranking. |
| 19 | 3 | The loader checks every row, then raises once with the full list of malformed rows (and also refuses if the fetch manifest recorded any bad JSON lines). | My call: one run shows every problem, not just the first; still no silent drops. |
| 20 | 3 | `Item` is pydantic strict + `extra="forbid"` + frozen. `average_rating` and `rating_number` are nullable. | My call: no type coercion, no fields outside the contract. Nullable because Step 4 must represent null/zero-rating edge cases, even though none occur in this data. |
| 21 | 3 | Priced-set C and m are stored in `reports/priors_fallback_<Category>.json` with `role = fallback_only_when_candidate_set_lt_30`; `load_fallback` refuses any file without that role. The whole-category `car_priors` in the Step 2 profile are descriptive only and are not read by ranking code. | User decision: candidate-set priors are the primary path; the global values are a fallback for sets under 30, never a default. |
| 22 | 4 | Candidate-set-mean C sensitivity is deferred to Step 7, once a real matcher exists. Step 4 varies C over the priced-set simple and count-weighted means only. | User decision: sensitivity results must come from the same matching logic the final system uses; a throwaway Step 4 matcher would not guarantee that. |
| 23 | 4 | The Step 4 sensitivity check runs over the whole priced pool (331,095 items), comparing every (C, m) setting pairwise, plus a raw-rating sort, rather than against a chosen baseline. | No candidate sets exist yet, and picking the fallback priors as a "baseline" would treat them as a default (#21). |
| 24 | 4 | CAR edge cases: v = 0 returns C exactly; v = null returns None (not computable), and those items rank last; v > 0 with a null rating raises; m <= 0 raises. | v = 0 is defined by the formula; an unknown count can't be weighted, and imputing v = 0 would invent evidence. A count without a rating is a contradictory record. |
| 25 | 4 | CAR ties are broken by more ratings first, then parent_asin. | Deterministic order. average_rating is rounded to 0.1 in the source (41 distinct values), so exact ties are common. |
| 26 | 4 | The < 30 fallback floor counts *rated* items in the candidate set, not raw set size. | Only rated items inform C and m. In this data every priced item is rated, so the two counts are identical. |
| 27 | 4 | **Needs justification before presenting.** m defaults to the median rating count: per candidate set at rank time (#12), and for the priced pool that median is 50, which is also the fallback value (#21). This is a convention, not a principled choice. | The sweep shows m decides the ranking: over the priced pool, m = 50 sits inside the transition between m = 25 and m = 120 (top-20 overlap with a plain star sort is 5/20 with simple C and 11/20 with count-weighted C, against 0/20 at m >= 120). The default has to be defended before the project is presented. Spike evidence bearing on this exists (indicative only): CONSIDERATIONS.md §11 and `spike/FINDINGS.md` on branch `spike/step7`. Status unchanged. |
| 28 | 7 | **Open question, to investigate at Step 7.** Per-query m values seen so far (54–123) straddle the transition the sweep found between m = 25 and m = 120. CAR may behave very differently across queries: near-inert on some candidate sets, decisive on others. | User flag. Caveat: 54–123 came from a throwaway Step 4 matcher that was reverted (#22). It is not reproducible from the repo and must be re-measured on the Step 7 matcher. Spike evidence bearing on this exists (indicative only): CONSIDERATIONS.md §11 and `spike/FINDINGS.md` on branch `spike/step7`. Status unchanged. |
| 29 | 5 | The audit set is a simple random sample of 200 from the priced pool (seed 20260930), not stratified. | It represents the pool the ranker actually sees; stratifying would need a product-type classifier nobody has built. |
| 30 | 5 | The extractor may read only the title plus a fixed list of details keys (`EXTRACTOR_DETAIL_KEYS`), and the audit CSV shows the labeller exactly those fields. Labels come from the file, not Amazon lookups. | Labels and extraction judged on the same evidence; the live listing may differ from the 2023 snapshot. |
| 31 | 5 | Truth format: `COUNT x SIZE UNIT`, `NONE` (not determinable), or `N/A` (single durable item). Correct = same dimension and total quantity within 1%; returning a pack size where truth is `NONE` counts as wrong. Coverage is reported beside precision, and precision is given with and without `N/A` items. | Total quantity is what NUP uses. Coverage stops abstention from inflating precision, and separating `N/A` stops trivial `1 x 1 ct` cases from inflating it. |
| 32 | 5 | The audit set is committed before any extractor code exists. The extractor is developed on a separate sample that excludes the 200 audit items, and audit rows aren't inspected during development. | Keeps the 90% precision number honest: the extractor isn't tuned to the set it's scored on, and git order shows the sequence. |
| 33 | 5 | The extractor collects *readings* (dimension and total quantity) from the title and details, groups those that agree within 2%, and assigns fixed confidence levels (0.95 / 0.85 / 0.80 / 0.75 / 0.60 / 0.30; see `unit_price.py`). Any disagreeing strong source means abstain. | "Never guess a pack size": a result needs agreement, or a single unambiguous source with nothing contradicting it. |
| 34 | 5 | Confidence threshold = 0.7, set in `config/unit_price.json` before any labels exist. Title-ambiguous (0.60) and contradicted (0.30) readings abstain; a single strong source (0.75) or better passes. | Picking the threshold after seeing precision would be tuning on the audit set. |
| 35 | 5 | `Item Weight` is never a source. `Number of Items` and `Item Package Quantity` only corroborate. A `Size` or `Unit Count` value outside Amazon's standard format (e.g. "24L") only corroborates. `Unit Count: 1` is ignored. | In development data these fields hold shipping or placeholder weight, mean pack count on some listings and piece count on others, or are filler. |
| 36 | 5 | If the title names a container (cup, glass, trash bag, lid, sleeve…), its weight and volume, and the details' weight and volume, are treated as capacity and dropped. Titles with "kit" or "includes" abstain. "25g protein" style nutrition amounts and mg dosages are never sizes. | These describe what the item holds or contains per dose, not what the price buys. Known miss: "pouch" is not treated as a container, because consumables use it too. |
| 37 | 5 | "N pack" with N <= 24 is a pack multiplier; above 24 it is a piece count ("600 Pack" spoons). A lone title multiplier that doesn't divide a details count evenly means abstain. | Judgment from development data; the audit will measure whether it holds. |
| 38 | 5 | The guardrail is judged on the point estimate of precision, per SPEC; a 95% Wilson interval is always reported beside it. Extractor coverage over the whole priced pool is reported too. | With about 100 extractions the interval is roughly ±6 points; hiding it would overstate what 200 labels can show. |
| 39 | 5 | Format-limited items (#62, #166, #184: lengths in yd/ft that the truth format can't express, so labelled NONE) are reported as a separate category (`audit/format_limited.json`). The pre-registered rule (#31), which counts them as wrong, stays the headline: 93.1%. The split is reported beside it: 95.3%. | User request, made after labelling. A rule change after seeing labels can't replace the rule fixed in advance; both are shown. |
| 40 | 5 | **Open question.** The truth format and the extractor have no length dimension (yd, ft, m), so tape, foil and ribbon rolls can't have a comparable unit price. Decide whether NUP should support length, or whether length-sold items should always fail open. | 3 of 200 audit items (1.5%) hit this. Adding a dimension means changing both the extractor and the audit format, then re-auditing. |
| 41 | 5 | **Open question.** #132 (paper bowls, "12 Oz … 50pcs") is labelled `50 x 12 oz`; the extractor treats 12 oz as capacity and returns `50 ct`. The labelling guide never said how to label container capacity, so this is a gap in the guide, not settled either way. Scored as wrong under the label as given. | If capacity is meant to be excluded (#36), the label would be `1 x 50 ct` and this would be correct: 94.3% pre-registered, 96.5% with the split. Not applied without the labeller's decision. |
| 42 | 5 | **Known mismatch, left as is.** The labelling guide (`audit/README.md`) lists `mg`, which the scorer rejects, and leaves out `gal`, `qt` and `pt`, which the scorer accepts. No label used `mg`, so no score was affected. The guide is not being rewritten. | Editing a labelling guide after labels exist is the kind of change that makes an audit unfalsifiable, even when harmless. The mismatch is recorded instead. |
